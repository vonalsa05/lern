## Вердикт

Стек рабочий и собран аккуратно: поднимается одной командой, зависимости ждут `service_healthy`, кэш реально отдаёт `source: redis` со второго запроса, все три экспортёра в Prometheus в состоянии `up`. Видно, что модули 01–11 не прошли мимо.

Но капстоун сдан не по своему ТЗ. Три вещи ломают всю конструкцию:

1. **Миграций нет** — это явный пункт acceptance criteria, и он не сделан.
2. **`/readyz` отвечает 200 при мёртвой БД** — readiness-проба, которая не краснеет, хуже, чем её отсутствие: балансировщик продолжит слать трафик в нерабочий инстанс.
3. **`checks/verify.sh` не умеет падать** — он печатает `All checks passed` на сломанном стенде. Это самый дорогой баг из трёх: он маскирует два предыдущих и любые будущие.

Общий счёт по проверке: **12 пунктов пройдено, 10 провалено**.

## Блокеры

### Б1. Миграций нет вообще

`psql -c '\dt'` → `Did not find any relations`. Ни SQL-файла, ни alembic, ни entrypoint-скрипта. Приложение и не пытается ничего читать из БД: `/readyz` делает `psycopg.connect()` и сразу закрывает соединение, `/hello` возвращает константу.

Как чинить: отдельный сервис `migrate` в том же compose — init-контейнер, который отрабатывает и умирает:

```yaml
  migrate:
    build: .
    restart: "no"
    command: ["alembic", "upgrade", "head"]
    depends_on:
      db:
        condition: service_healthy

  api:
    depends_on:
      migrate:
        condition: service_completed_successfully
```

`service_completed_successfully` — ровно то условие, ради которого этот паттерн существует: API не стартует, пока миграции не проехали. Если alembic избыточен — хватит `psql -f /migrations/001_init.sql`, главное, чтобы миграция была идемпотентной и запускалась сама.

### Б2. `/readyz` врёт

Проверено: `docker compose stop db`, затем `curl -w '%{http_code}' /readyz` → **200** с телом `{"status": "not ready"}`.

Readiness — это не «текст о состоянии», это контракт с балансировщиком: 200 = шли трафик, любой другой код = выведи из ротации. Тело читают люди, код читают машины.

```python
@app.get("/readyz")
def readyz():
    deps = {}
    try:
        with psycopg.connect(DATABASE_URL, connect_timeout=2) as conn:
            conn.execute("select 1")
        deps["db"] = "ok"
    except Exception as exc:
        deps["db"] = f"down: {exc.__class__.__name__}"
    try:
        cache.ping()
        deps["cache"] = "ok"
    except Exception as exc:
        deps["cache"] = f"down: {exc.__class__.__name__}"

    if all(v == "ok" for v in deps.values()):
        return deps
    raise HTTPException(status_code=503, detail=deps)
```

Заодно: `/healthz` при мёртвой БД обязан остаться 200 — иначе Docker или Kubernetes начнёт перезапускать здоровый контейнер, у которого просто нет БД. Сейчас это сделано правильно, не сломай при правке.

### Б3. Redis не проверяется в readiness

При погашенном кэше `/hello` отдаёт **500**, а `/readyz` при этом рапортует «ready». Redis у тебя hard-dependency (кода деградации на промах соединения нет), значит он обязан быть в readiness. Либо — и это интереснее — сделать его soft-dependency: при недоступном кэше ходить в БД напрямую и писать метрику `cache_errors_total`. Тогда падение Redis становится просадкой скорости, а не отказом сервиса.

### Б4. `verify.sh` не умеет падать

Сейчас он дёргает `curl -fsS /readyz`, а 200 его устраивает — и на стенде без единой таблицы, с мёртвой БД в фоне, он честно печатает `All checks passed`.

Проверка ценна ровно тем, что краснеет. Правила: `set -euo pipefail`, каждая проверка — отдельный именованный пункт, в конце ненулевой код возврата, и обязательно хотя бы одна **негативная** проверка (сломали зависимость → убедились, что сервис это признал).

### Б5. Нет backup/restore, Makefile и README решения

`README.md` модуля прямо требует `backup/restore` скрипт для БД и структуру `lab/<трек>/solution/` с `Makefile` и `README.md`. Решение лежит не там, где просили, без обоих файлов, `answers.md` не заполнен. Бэкап без проверенного восстановления бэкапом не является: скрипт должен уметь `dump → down -v → restore → данные на месте`.

## Ошибки конфигурации

**К1. `latest` в двух образах.** `prometheuscommunity/postgres-exporter` и `oliver006/redis_exporter` указаны без тега. Это ровно тот пункт, от которого предостерегает `broken/common-failures.md` в том же модуле. Плюс собранный образ `api` нигде не получает релизного тега — добавь `image: web-db-cache:1.0.0` рядом с `build: .`.

**К2. Лимиты и ротация логов не у всех.** `docker inspect` показывает `Memory=0`, `NanoCpus=0` и пустой `max-size` у `postgres-exporter` и `redis-exporter`. Дублирование блоков в compose лечится якорем:

```yaml
x-logging: &logging
  driver: json-file
  options:
    max-size: "10m"
    max-file: "3"

services:
  redis-exporter:
    logging: *logging
```

**К3. `restart` не выставлен нигде.** У всех восьми контейнеров `RestartPolicy=no`. После перезагрузки машины стенд мёртв. Нужно `restart: unless-stopped` всем долгоживущим сервисам (и осознанно `"no"` у `migrate`).

**К4. У `api` нет healthcheck.** В `docker compose ps` он единственный без `(healthy)`, хотя в quickstart README он есть и у всех остальных сервисов он написан. Без него нельзя навесить `depends_on: api: condition: service_healthy` — например, на будущий нагрузочный контейнер.

**К5. `api` работает от root.** `Config.User` пуст, rootfs на запись, `cap_drop` нет. Общий чеклист модуля требует non-root — и в соседнем треке `Security-first` ты это уже умеешь. Перенеси оттуда: `USER app` в Dockerfile, `read_only: true` + `tmpfs: [/tmp]` + `cap_drop: [ALL]` + `security_opt: [no-new-privileges:true]` в compose.

**К6. Пароль виден в `docker inspect` у трёх контейнеров.** `POSTGRES_PASSWORD`, `DATABASE_URL` и `DATA_SOURCE_NAME` содержат его открытым текстом. Минимум — `.env` + `env_file` (и `.env` в `.gitignore`). Правильно — `POSTGRES_PASSWORD_FILE` и `secrets:`, как в `Security-first`. Кстати, там же `secrets/app_secret.txt` закоммичен в git — это ровно тот failure-mode, от которого трек и защищает, убери его из индекса.

**К7. Redis под лимитом памяти без эвикции.** Проверено: `maxmemory 0`, `maxmemory-policy noeviction` при `memory: 256M`. Под нагрузкой контейнер поймает OOM-kill вместо вытеснения старых ключей — то есть кэш умрёт вместо того, чтобы работать чуть хуже.

```yaml
  cache:
    command: ["redis-server", "--maxmemory", "200mb", "--maxmemory-policy", "allkeys-lru"]
```

RDB-снапшоты, к слову, работают: дефолтные `save 3600 1 / 300 100 / 60 10000` активны, и volume `/data` не бесполезен. Но реши осознанно, нужен ли кэшу persistence вообще — если нет, volume лучше убрать, чтобы не создавать иллюзию durability.

**К8. Ложная зависимость `prometheus → cadvisor`.** Prometheus не нуждается в cAdvisor для старта: не отвечающий таргет — нормальное состояние, скрейп ретраится сам. А с `start_period: 90s` эта зависимость тормозит холодный запуск всего стенда. Убери `depends_on` у Prometheus целиком.

**К9. Мониторинг есть, наблюдаемости нет.** `GET /metrics` → **404**. Есть метрики контейнеров, Postgres и Redis — то есть видно, что «плохо», но не видно, **почему**: нет RPS, нет распределения задержек, нет cache hit ratio. Plus Prometheus не скрейпит сам себя, а значит не видно, не отвалился ли скрейп.

```python
from prometheus_client import Counter, Histogram, make_asgi_app
app.mount("/metrics", make_asgi_app())
```

И джоб в `prometheus.yml`:

```yaml
  - job_name: api
    static_configs:
      - targets: ["api:8080"]
  - job_name: prometheus
    static_configs:
      - targets: ["localhost:9090"]
```

**К10. Grafana без provisioning.** Пустой volume, datasource и дашборды заводятся руками, логин `admin/admin`. После `down -v` всё заново — то есть дашборд не является частью проекта. Лечится каталогом `grafana/provisioning/{datasources,dashboards}` с YAML и JSON дашборда в репозитории.

Комментарий про это в `compose.yaml:136-137` побился — кириллица вырезалась, осталось `#  volume ,   Grafana,`. Проверь кодировку в редакторе, файл должен быть UTF-8.

**К11. Всё торчит на 0.0.0.0.** Порты 8080, 9090, 3000, 8081 слушают на всех интерфейсах. На реальной машине это Prometheus, cAdvisor и Grafana с `admin/admin`, открытые в интернет. Служебные UI биндить на `127.0.0.1:` и ходить через `ssh -L`, наружу оставить только API.

**К12. Код приложения.** `redis.from_url(REDIS_URL)` вызывается на уровне модуля: если переменная не задана, контейнер падает на импорте с невнятным `TypeError`. Нет `decode_responses=True` (отсюда ручной `.decode()`), нет таймаутов соединения, а к Postgres на каждый запрос создаётся новый коннект без пула — при нагрузке это первое, что упрётся в потолок. Смотри `psycopg_pool.ConnectionPool`.

**К13. Dockerfile.** Зависимости не запинены — по факту приехали `fastapi==0.141.1`, `redis==8.1.0`, завтра приедут другие, и сборка перестанет быть воспроизводимой. Нет `.dockerignore` (в `Security-first` он есть), нет `USER`, нет `HEALTHCHECK`, один stage на 202 МБ.

**К14. cAdvisor отдаёт неполные метрики.** Монтирование `/var/lib/docker:ro` закомментировано — метрики по слоям и дисковому потреблению контейнеров собираться не будут.

## Задача на проект: SLO-стенд, который умеет ломаться

### Идея

Текущий капстоун доказывает, что стек **поднимается**. Следующий должен доказывать, что стек **работает под нагрузкой и правильно деградирует**, когда зависимости отказывают.

Стенд сам себя проверяет: генератор нагрузки бьёт по API заданным RPS, в сеть до Postgres и Redis вносятся задержки и обрывы, дашборд показывает, как деградирует SLO, а проверка подтверждает, что сервис деградировал **правильно** — потеряв скорость, но не данные, и честно сообщив о своём состоянии.

Всё на одной машине, около десяти контейнеров, примерно 1.5 ГБ RAM.

### Архитектура

```text
[k6]  →  [traefik :80]  →  [api ×2 (blue/green)] ─┬→ [toxiproxy] → [postgres] ← [backup]
                                                  └→ [toxiproxy] → [redis]
[migrate] отрабатывает и умирает
[prometheus] ← api:/metrics, cadvisor, экспортёры
[grafana + alertmanager] ← provisioning из репозитория
```

Ключевая деталь: API ходит в БД и кэш **через Toxiproxy**. Это позволяет портить сеть на лету, не трогая ни код, ни контейнеры зависимостей: `toxiproxy-cli toxic add db --type latency --attribute latency=300`.

### Контракт API

Нагрузочные скрипты уже написаны под него, поэтому эндпоинты именно такие:

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/healthz` | 200, без обращения к зависимостям |
| GET | `/readyz` | 200 или **503** с перечислением состояния зависимостей |
| GET | `/metrics` | метрики Prometheus, включая гистограмму задержек |
| POST | `/links` | 201 `{"code": "..."}`, пишет в Postgres |
| GET | `/links/{code}` | 200 `{"url": "...", "source": "cache\|db"}` + заголовок `X-Cache: HIT\|MISS`, или 404 |

Сервис — сокращатель ссылок. Выбран потому, что даёт естественную смесь записи и чтения с кэшем и осмысленный hit ratio.

### Этап 1 — честная база

Цель: довести текущий стек до состояния, в котором заявленные acceptance criteria действительно выполняются.

1. **Миграции** отдельным init-контейнером, `api` ждёт `service_completed_successfully`. Схема: таблица `links(code primary key, url, created_at)`.
2. **Эндпоинты** по контракту выше. `/readyz` отдаёт 503 при недоступности любой зависимости, `/healthz` остаётся 200 всегда.
3. **Метрики приложения**: счётчик запросов с лейблами метода, маршрута и кода ответа; гистограмма задержек; счётчики попаданий и промахов кэша. Джобы `api` и `prometheus` в `prometheus.yml`.
4. **Dockerfile**: версии зависимостей запинены, multi-stage, `USER app`, `.dockerignore`, `HEALTHCHECK`.
5. **Compose**: `.env` вместо паролей в открытом виде, `restart: unless-stopped`, лимиты и ротация логов **всем** сервисам, явные теги **всем** образам, `image: web-db-cache:1.0.0` рядом с `build:`, `maxmemory`/`allkeys-lru` у Redis, убрать `depends_on` у Prometheus.
6. **`checks/verify.sh`** — из комплекта, прогоняется без правок.

**Критерий приёмки этапа:**

```bash
docker compose down -v && docker compose up -d && ./checks/verify.sh   # зелёный, код 0
docker compose stop db && ./checks/verify.sh                           # красный, код 1
```

Второе важнее первого. Проверка, которая не краснеет на сломанном стенде, ничего не проверяет.

### Дальше — по одному этапу за раз

- **Этап 2.** Grafana с provisioning из репозитория: datasource и дашборд кодом, плюс Alertmanager с правилом «p95 чтений выше 300 мс дольше двух минут».
- **Этап 3.** Backup и restore Postgres с проверкой цикла: записали → сняли дамп → `down -v` → восстановили → данные на месте.
- **Этап 4.** Toxiproxy и k6: нагрузка в профиле compose, сценарии «медленная БД» и «мёртвый кэш», пороги SLO как критерий приёмки.
- **Этап 5.** Traefik и blue-green выкатка новой версии API без простоя под работающей нагрузкой.

### Как сдавать

Структура — та, которую требует README модуля: `lab/web-db-cache/solution/` с `compose.yaml`, `Dockerfile`, `Makefile`, `README.md` и `checks/`. В `README.md` решения — архитектура, команды запуска, список принятых компромиссов. В `answers.md` — заполненные разделы, особенно «Риски и компромиссы»: там интереснее всего видно ход мысли.

Коммиты атомарные, с семантическими префиксами (`feat:`, `fix:`, `chore:`), по одной теме на коммит. Каждый этап — отдельный pull request: так ревью проходит быстрее и предметнее.
