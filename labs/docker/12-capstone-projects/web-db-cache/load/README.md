# Нагрузочное задание

Два скрипта k6 — это **исполняемое ТЗ**, а не часть решения. Они описывают, что сервис обязан уметь, и умеют краснеть, когда он этого не умеет. Реализация — твоя.

Версия k6: **2.2.0**. Скрипты прогнаны и на здоровом стенде (PASS), и на намеренно испорченном (FAIL, код возврата 99).

---

## Контракт API

Скрипты написаны под эти эндпоинты, поэтому реализовать нужно именно их:

| Метод | Путь | Ожидается |
|---|---|---|
| GET | `/healthz` | 200, без обращения к БД и кэшу |
| GET | `/readyz` | 200, если зависимости живы; **503**, если нет. В теле — состояние каждой зависимости |
| GET | `/metrics` | формат Prometheus, включая гистограмму `*_duration_seconds_bucket` |
| POST | `/links` | 201, тело `{"code": "..."}`, запись в Postgres |
| GET | `/links/{code}` | 200, тело `{"url": "...", "source": "cache\|db"}`, или 404 |

Источник ответа скрипты определяют по заголовку `X-Cache: HIT\|MISS`, а если его нет — по полю `source` в теле. Достаточно одного из двух, выбирай сам.

## `smoke.js` — контрактный тест

Одна итерация, порог `checks==1.0`: любое нарушение контракта роняет прогон с кодом 99. Запускать перед каждой нагрузкой — бессмысленно мерить задержки у сервиса, который отвечает не то.

Что проверяет: коды ответов всех пяти эндпоинтов, что `/healthz` не ходит в зависимости (укладывается в 50 мс), что `/metrics` отдаёт гистограмму, что первое чтение — промах кэша, второе — попадание, и что кэш отдаёт тот же `url`, что и БД.

## `slo.js` — нагрузочный сценарий

Три сценария: `warmup` (разгон 0 → RPS), `reads` (постоянный RPS) и `writes` (постоянный WRITE_RPS). Решения, которые в нём приняты, и которые стоит понять до запуска:

**Открытая модель нагрузки.** Executor — `arrival-rate`, а не `constant-vus`. Нагрузка задаётся в запросах в секунду и не замедляется, когда сервис деградирует. Closed-модель на умирающем сервисе рисует красивую картинку: виртуальные пользователи ждут ответа, значит новых запросов шлют меньше, значит нагрузка сама себя снижает ровно тогда, когда должна была вскрыть проблему. Открытая модель ведёт себя как реальные пользователи, которым всё равно, что тебе плохо.

**Разогрев исключён из SLO.** На холодном кэше все чтения — промахи, и hit ratio за весь прогон получился бы заниженным, а p95 — завышенным. Поэтому `warmup` помечен отдельным тегом и в пороги не входит.

**Перекос 80/20.** 80% чтений идут в 20% ключей. На равномерном распределении кэш бесполезен, а hit ratio ничего не говорит о реальной нагрузке.

**`dropped_iterations` — это тоже порог.** Метрика растёт, когда k6 не успел выдать заданный RPS имеющимися VU. Ненулевое значение означает, что нагрузка была меньше заявленной и остальные цифры относятся к другому эксперименту.

Сводка печатается в терминах SLO, полный дамп метрик k6 пишется в `/results/summary.json`.

## Параметры

Всё через переменные окружения, править скрипты не нужно:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `API_URL` | `http://localhost:8080` | адрес сервиса |
| `RPS` | `50` | целевые чтения в секунду |
| `WRITE_RPS` | `5` | записи в секунду |
| `DURATION` | `2m` | длительность замера |
| `WARMUP` | `30s` | длительность разогрева |
| `SEED_LINKS` | `200` | сколько ссылок засеять перед замером |
| `P95_MS` | `300` | бюджет задержки чтения, мс |
| `HIT_RATIO` | `0.8` | минимальный hit ratio кэша |

Пороги считаются от `P95_MS`: чтения `p95 < P95_MS` и `p99 < P95_MS × 3`, записи `p95 < P95_MS × 2`.

## Как запустить

Каталог для отчётов должен быть доступен на запись пользователю k6 (uid 12345):

```bash
mkdir -p load/results && chmod 0777 load/results
```

Стек уже поднят, поэтому k6 достаточно подключить к его сети (`<имя_проекта>_default`, посмотреть можно через `docker network ls`):

```bash
docker run --rm \
  --network web-db-cache_default \
  -v "$PWD/load:/scripts:ro" \
  -v "$PWD/load/results:/results" \
  -e API_URL=http://api:8080 \
  grafana/k6:2.2.0 run /scripts/smoke.js
```

Тот же вызов с `/scripts/slo.js` и нужными `-e` запускает замер. Код возврата: `0` — уложился в SLO, `99` — нарушен хотя бы один порог.

## Задание

**А. Контракт.** Реализовать пять эндпоинтов и добиться зелёного `smoke.js`. Это часть этапа 1 проекта: без `/metrics` и честного `/readyz` смысла в нагрузке нет.

**Б. SLO.** Добиться зелёного `slo.js` на значениях по умолчанию: 50 rps чтений, p95 до 300 мс, hit ratio выше 0.8. Если не укладываешься — сначала посмотри в `summary.json` и в свои же метрики, а не подкручивай пороги. Подкрутить можно в конце, осознанно, записав в `answers.md`, почему выбран другой бюджет.

**В. Интеграция в compose.** Завести k6 сервисом под профилем, чтобы он не поднимался при обычном `docker compose up -d`, и чтобы прогон был одной командой через `Makefile`.

**Г. Хаос.** Поставить Toxiproxy между `api` и зависимостями, перенаправить в него `DATABASE_URL` и `REDIS_URL`, написать скрипт добавления задержек и обрывов. Показать два прогона: здоровый — зелёный, с задержкой 300 мс до Postgres — красный. В `answers.md` объяснить, какие метрики на дашборде при этом сдвинулись и почему.

**Критерий приёмки:** `smoke.js` зелёный, `slo.js` зелёный на здоровом стенде и красный под хаосом, прогон запускается одной командой, `summary.json` сохраняется.

## Чего здесь намеренно нет

Ни compose-обвязки, ни конфига Toxiproxy, ни заглушки API. Это и есть работа по пунктам В и Г — если выдать их готовыми, задание сведётся к запуску чужих команд.

Сами скрипты менять не нужно: всё, что предполагалось настраивать, вынесено в переменные окружения. Если для прохождения теста хочется поправить тест — это сигнал, что проблема в сервисе.
